## Engineering approach

I prefer systems that are easy to reason about over systems that are impressive only on paper.

Architecture should make responsibilities clear. Abstractions should solve an actual problem. Tests should protect behavior that matters. Documentation should explain decisions that are not obvious from the code.

I use modern development tools extensively during implementation, debugging and review. They improve iteration speed, but they do not replace understanding the system, reviewing the output or validating what gets shipped.

<br>

## Project standards

Public projects are built with the same basic expectations I would want when joining an existing codebase.

| Area | Standard |
| :--- | :--- |
| Architecture | Responsibilities and boundaries documented |
| Setup | Reproducible local installation |
| Configuration | Environment variables documented with safe examples |
| Quality | Formatting, linting, type checking and automated tests |
| Security | Secrets excluded, dependencies reviewed and inputs validated |
| Database | Versioned schema changes and reproducible migrations |
| CI | Automated validation before changes are accepted |
| Documentation | Setup, architecture and important decisions kept with the code |
| Operations | Errors and important system behavior observable where appropriate |
